# AInterview 平台——AI 驱动的全流程求职赋能平台

---

## 摘要

当前大学生就业市场竞争日益激烈，应届毕业生在简历撰写和面试表现两大核心环节面临突出问题：简历难以凸显个人核心竞争力，面试因紧张与技巧不足导致发挥失常。线下专业求职指导成本高昂，难以满足应届生即时性、个性化的指导需求。针对上述问题，本文设计并实现了一款名为 AInterview 的 AI 驱动全流程求职赋能 Web 平台。

系统采用前后端分离的 B/S 架构：前端基于 Vue3 框架与 Element Plus 组件库构建用户界面，集成 face-api.js 面部表情识别库与浏览器原生 Web Speech API 实现面试过程中的情绪监测与语音转文字；后端基于 Django 框架与 Django REST Framework 开发 RESTful API，集成 DeepSeek 大语言模型实现 AI 面试出题、追问、反馈与报告生成，集成 PaddleOCR 引擎实现简历文件的OCR解析。系统采用 MySQL 作为关系型数据库，Redis 提供缓存服务与实时通信 Channel Layer，RabbitMQ 作为 Celery 异步任务队列的消息代理。实时通信方面，面试答题环节采用 SSE（Server-Sent Events）实现 AI 流式追问推送，AI 对话与用户聊天环节采用 WebSocket（Django Channels）实现双向实时通信。简历 PDF 导出功能通过 Electron 无头浏览器窗口配合 Chromium printToPDF 引擎实现 A4 精确分页输出。

经本地开发环境测试，系统已完成 AI 模拟面试、智能评估报告生成、简历智能生成与管理、操作日志、AI 参数配置等核心功能的端到端闭环。测试结果表明，系统能够实现基于岗位的 AI 动态出题、流式追问、面部表情实时分析、多维度评估报告异步生成、简历文件 OCR 解析与 AI 对话式生成、A4 PDF 导出等功能。同时，本文对 OCR 解析精度、AI 接口调用延迟、面部识别兼容性等现有不足进行了分析并提出了改进方案。

**Keywords:** AI Interview, Django REST Framework, Vue3, DeepSeek, face-api.js

## 第一章 绪论

### 1.1 研究背景与意义

近年来，我国高等教育毕业生人数持续高位运行，就业市场竞争压力不断增大。据统计，2025 届全国普通高校毕业生规模已突破 1170 万人，创历史新高。在如此激烈的求职环境中，应届毕业生普遍缺乏系统的求职实战训练，在两大核心环节存在显著短板：其一，简历撰写方面，多数毕业生难以准确把握企业用人需求，简历内容往往流于表面，无法有效凸显个人核心竞争力与企业岗位的匹配度；其二，面试表现方面，由于缺乏实战经验，毕业生在面试过程中常因紧张情绪、应答逻辑不清、表达技巧欠缺等原因导致发挥失常，错失就业机会。

与此同时，线下专业的求职指导服务收费普遍较高。一对一职业规划咨询、简历优化服务、模拟面试培训等课程的单次费用通常在数百至数千元不等，对于广大应届毕业生群体而言成本过于高昂。此外，传统线下服务受时间和空间限制，难以提供即时性响应和规模化服务。

人工智能技术的快速发展为解决上述困境提供了新的可能。以 DeepSeek 为代表的大语言模型在自然语言理解与生成方面展现出卓越能力，能够模拟专业面试官进行对话式交互，提供个性化的面试提问、追问与反馈；在简历优化方面，大模型能够根据岗位需求进行内容诊断、语言润色和结构优化。与此同时，浏览器端的面部表情识别（face-api.js）和语音识别（Web Speech API）技术的成熟，使得在前端实时采集面试者的情绪状态与语音输入成为可能，为面试评估提供了多维度数据支撑。

基于上述背景，本文设计并实现了 AInterview 平台——一款 AI 驱动的全流程求职赋能 Web 应用。平台面向高校毕业生群体，提供永久免费的 AI 模拟面试、智能评估报告生成、简历智能生成与优化等核心服务，旨在降低求职准备门槛，缩短简历制作时长，压缩面试准备周期，提升简历筛选通过率与面试成功率。

从技术实践角度看，通过本项目的全流程开发，可系统掌握 Django REST Framework 后端开发、Vue3 前端工程化设计、MySQL 数据库建模、Celery 异步任务处理、DeepSeek 大模型 API 集成、Django Channels 实时通信、Electron 桌面应用开发等核心技术，全面锻炼全栈开发与工程实践能力。

从社会价值角度看，本课题探索了 AI 技术在高校就业服务领域的落地应用，为"人工智能+教育"模式提供了具体的技术解决方案和可参考的实现路径，具有一定的实践参考价值。

### 1.2 国内外研究现状

**在线模拟面试平台**

在国内外市场，已涌现出多种在线模拟面试产品。国内方面，牛客网提供面向互联网技术岗位的在线笔试与模拟面试服务，侧重编程能力的自动化评测；赛码网聚焦于大型企业的校招在线笔试环节，面试模拟功能相对有限。国外方面，HireVue 是一家知名的 AI 视频面试平台，通过分析候选人的视频回答中的语言内容、语音语调、面部微表情等多维度信息给出评估分数，已被联合利华、希尔顿等大型企业采用；Yobs 同样提供异步视频面试服务，通过 AI 分析候选人的沟通能力、性格特质等软技能。

然而，上述产品存在三方面局限：第一，多数产品面向企业端收费，个人用户使用成本高或功能受限；第二，功能多为预先录制视频的单向评估，缺乏 AI 实时追问的交互式面试体验；第三，部分产品仅覆盖面试环节，未能与简历优化、求职数据分析等上下游环节形成闭环。

**AI 辅助简历工具**

在简历优化领域，国内外出现了多款 AI 辅助工具。国内方面，超级简历、五百丁等平台提供了在线简历编辑和模板选择功能，部分产品开始引入 AI 评分和关键词优化功能；猎聘、BOSS 直聘等招聘平台也推出了基于 AI 的简历优化建议。国外方面，Zety、Resume.io、Kickresume 等平台提供了丰富的简历模板和 AI 内容建议功能；Rezi 则专注于 ATS（Applicant Tracking System，求职者追踪系统）优化，帮助求职者制作更易被企业筛选系统识别的简历。

现有工具的主要不足在于：AI 诊断功能多停留在关键词匹配的浅层次分析，缺乏对简历内容与 JD（Job Description，岗位描述）之间深度语义匹配的评估；部分工具采用全量重写的生成方式，无法实现增量式的精细化优化，且Token消耗量较大。

**面部识别技术在面试评估中的应用**

将面部表情识别技术应用于面试评估是近年来的研究热点。学术界的研究主要集中在利用深度卷积神经网络（如 MobileNet、ResNet 等）对面部关键点进行定位并分类情绪状态。在工程应用层面，face-api.js 是基于 TensorFlow.js 的浏览器端人脸识别库，通过 TinyFaceDetector 进行人脸检测、FaceExpressionNet 进行情绪分类，支持中性、开心、悲伤、惊讶、恐惧、厌恶、愤怒七种基础情绪的实时识别，为前端集成提供了低门槛的解决方案。

现有的面部识别面试产品（如 HireVue）将面部表情作为整体评分的一个维度，但其算法存在争议：不同种族、性别、光线条件下的表现差异较大，且情绪与面试能力之间的因果关系尚缺乏充分验证。国内将面部识别应用于模拟面试的产品较少，且多以单机软件形式存在，浏览器端的 Web 集成方案尚不成熟。

**现有方案的不足与本文切入点**

综合上述分析，现有方案存在以下不足：（1）缺乏面试+简历+数据分析的全流程一体化整合平台，求职者在不同工具间切换效率低；（2）多数产品以企业付费为导向，个人免费使用体验有限；（3）AI 交互以单向评估为主，缺乏深层追问和对话式交互；（4）技术栈以 Java 或云端 API 为主，鲜有采用 Python Django + Vue3 开源全栈方案的产品，学术研究的可复现性不足。

本文的研究切入点在于：构建一个面向个人用户的免费全流程求职赋能平台，整合 AI 模拟面试（含面部表情分析和语音识别）、智能评估报告、AI 对话式简历生成与诊断、操作日志与成长看板等模块于一体，采用开源技术栈实现，探索 AI 技术在高校就业服务中的综合应用。

### 1.3 课题研究内容

本文的主要研究内容包括以下四个方面：

（1）**AI 模拟面试系统**：研究基于大语言模型的动态面试出题策略，实现根据目标岗位、简历背景和面试难度自动生成面试题目；研究 SSE 流式推送技术用于 AI 追问场景；研究浏览器端面部表情实时识别与语音转文字技术的集成方法；研究面试会话状态管理、中断恢复等工程实现。

（4）**辅助功能模块**：研究操作日志的跨表数据聚合与可视化展示；研究 Django Channels 的 WebSocket 实时通信在 AI 对话与用户聊天场景中的应用。

## 第二章 相关技术与理论

### 2.1 前端技术

**Vue3 框架与 Vite 构建工具**

Vue3 是 Vue.js 框架的第三个大版本，于 2020 年正式发布。其核心改进在于引入了基于 Proxy 的响应式系统，替代了 Vue2 中基于 Object.defineProperty 的实现，解决了后者在数组变更检测和对象属性动态添加方面的局限。Vue3 的 Composition API 提供了比 Options API 更灵活的代码组织方式，通过组合式函数（Composables）实现逻辑复用，特别适用于中大型单页应用的开发。本系统中，面部表情识别（useFaceApi）、语音识别（useSpeechRecognition）、TTS 语音合成（useTTS）、PDF 导出（useExport）、简历渲染（useResumeRenderer）等核心功能均以 Composables 形式封装，实现了业务逻辑与组件视图的分离。

Vite 是由 Vue.js 作者尤雨溪开发的新一代前端构建工具，利用浏览器原生 ES Module 支持实现了开发环境下的秒级热更新，显著提升了开发体验。在生产环境下，Vite 基于 Rollup 进行打包，输出高度优化的静态资源。

**Element Plus 组件库**

Element Plus 是 Element UI 的 Vue3 适配版本，提供了按钮、表单、表格、对话框、消息提示等丰富的 UI 组件。系统选择 Element Plus 作为基础组件库，主要考虑其与 Vue3 的深度兼容、完善的中文文档以及活跃的社区维护。在样式方面，系统基于 DESIGN.md 设计规范对 Element Plus 默认样式进行了品牌化定制，使用 CSS 变量统一管理颜色、字体和间距体系，并通过 SCSS 变量覆盖实现了与品牌视觉风格的对齐。

**TypeScript 类型系统**

TypeScript 是微软开发的 JavaScript 超集，增加了静态类型检查功能。系统全部前端代码采用 TypeScript 编写，通过接口（interface）和类型别名（type）定义了 API 响应数据、通知类型、操作日志、简历内容等核心数据结构，在编译阶段即可捕获大量潜在的类型错误。

**Pinia 状态管理**

Pinia 是 Vue3 官方推荐的状态管理库，替代了 Vue2 时代的 Vuex。Pinia 采用组合式 API 风格定义 Store，支持 TypeScript 类型推导，去除了 Mutation 概念，简化了状态管理流程。系统使用 Pinia 管理用户认证状态、操作日志、聊天消息、简历编辑状态、AI 设置等全局共享数据，通过 defineStore 创建的 Store 模块在组件中按需引用。

### 2.2 后端技术

**Django 框架**

Django 是一个由 Python 编写的高级 Web 框架，遵循 MVT（Model-View-Template）设计模式和" batteries-included"（内置电池）理念。Django 内置了 ORM（对象关系映射）、身份认证系统、管理后台、表单处理、模板引擎、中间件等全套 Web 开发基础设施，使开发者能够快速构建功能完善的 Web 应用。

选择 Django 而非 Java Spring Boot 的主要考量是：其一，Python 是 AI/机器学习生态的核心语言，直接使用 Django 调用 DeepSeek API、集成 PaddleOCR 等 AI 相关库更为自然，无需维护跨语言调用层；其二，Django 的 ORM 通过 Python 类直接定义数据模型，迁移管理（Migrations）内置于框架中，开发效率更高；其三，Django 的管理后台（Admin）功能强大，通过简单的注册代码即可为管理员用户生成完整的 CRUD 界面，适合本系统的后台管理需求。

**Django REST Framework（DRF）**

Django REST Framework 是 Django 生态中最成熟的 RESTful API 开发工具包。其核心组件包括：Serializer（序列化器，将模型实例与 JSON 之间互相转换）、ViewSet（视图集，将一组 RESTful 动作封装为单一类）、Router（路由器，自动生成 URL 配置）以及认证、权限、节流、分页、过滤等可插拔的中间组件。

本系统中，所有 API 接口均通过 DRF 开发，配置了全局 JWT 认证、标准分页（每页 20 条）、基于 drf-spectacular 的 OpenAPI Schema 自动生成等基础能力。

**Simple JWT 身份认证**

JSON Web Token（JWT）是一种轻量级的、基于 JSON 的开放标准（RFC 7519），用于在通信双方之间传递被签名的声明信息。djangorestframework-simplejwt 是 DRF 生态中最常用的 JWT 实现库。

本系统的认证流程如下：用户提交邮箱和密码至登录接口，后端通过 django-allauth 验证用户凭据，验证通过后签发一对 Token——Access Token（有效期 2 小时，用于每次 API 请求的身份验证）和 Refresh Token（有效期 7 天，用于在 Access Token 过期后获取新的 Access Token）。前端将 Token 存入 Pinia Store，通过 axios 请求拦截器自动在每次请求的 HTTP 头部附加 Authorization: Bearer <access_token>。当后端返回 401 未授权状态码时，前端自动使用 Refresh Token 换取新的 Access Token 后重试原请求，用户无感知。

相比传统的基于 Session 的认证方式，JWT 的无状态特性更适合前后端分离架构：服务器无需存储 Session 信息，水平扩展时无需 Session 同步，Token 自身包含用户身份和过期时间等声明信息。

**drf-spectacular（OpenAPI 文档）**

drf-spectacular 是 DRF 的 OpenAPI 3.0 Schema 生成工具，能够从 DRF ViewSet、Serializer 的定义中自动提取接口信息生成标准的 OpenAPI 规范文件。配合 Swagger UI 渲染，在 `/api/v1/schema/swagger-ui/` 地址提供可交互的 API 文档界面，支持在线测试接口调用。选择 drf-spectacular 而非 drf-yasg 的原因在于后者对 OpenAPI 3.0 的支持已不活跃，而 drf-spectacular 是 DRF 社区当前推荐的方案。

### 2.3 数据存储与异步任务

**MySQL 关系型数据库**

MySQL 8.0 是世界上使用最广泛的开源关系型数据库管理系统之一。选择 MySQL 作为主数据库的考量包括：成熟稳定、社区支持广泛、Django ORM 对 MySQL 有完善的支持、utf8mb4 字符集支持完整的 Unicode 编码（包括 Emoji 等 4 字节字符）。本系统使用 MySQL 8.0 存储全部业务数据，包括用户信息、面试会话、题目与回答、简历内容与结构数据、博客文章与评论、操作日志、社交互动记录等。

数据库设计中，所有表强制使用 InnoDB 存储引擎以支持事务和外键约束；对高频查询字段（如 user_id、is_read、timestamp、status）建立索引以优化查询性能；对于多对多关系（如文章的标签、对话的参与者）通过 Django ORM 自动生成的中间表管理。

**Redis 缓存与 Channel Layer**

Redis 是一个开源的高性能键值对内存数据库，支持字符串、哈希、列表、集合、有序集合等多种数据结构。本系统中 Redis 的三大用途：其一，作为 Django 缓存后端（DB 1），缓存高频查询结果，如面试参考答案（TTL 1 小时）、文章推荐列表（TTL 24 小时）；其二，作为 Celery 任务结果存储后端（DB 2），持久化异步任务的执行结果；其三，作为 Django Channels 的 Channel Layer（DB 3），在多进程/多服务器之间转发 WebSocket 消息，是 WebSocket 跨进程实时通信的关键基础设施。

**Celery 分布式任务队列与 RabbitMQ**

Celery 是一个基于分布式消息传递的异步任务队列框架，广泛应用于需要将耗时操作从 Web 请求主线程中分离出来的场景。RabbitMQ 是一个实现了 AMQP（Advanced Message Queuing Protocol，高级消息队列协议）的消息中间件，以其可靠性、灵活的路由能力和完善的持久化机制而著称。

选择 RabbitMQ 而非 Redis 作为 Celery Broker 的原因是：RabbitMQ 是 Celery 官方推荐的 Broker，提供了消息确认（Acknowledgement）、持久化和更细粒度的路由控制，在任务可靠性和生产环境稳定性方面优于 Redis。本系统中，Celery 负责三类异步任务：面试评估报告的 AI 分析与生成、定时清理超时的面试会话（每 15 分钟扫描一次，将 30 分钟以上未活动的进行中面试自动标记为已取消）、博客每日数据统计（每晚 23:50 执行）。

### 2.4 AI 大语言模型接口

**DeepSeek 大模型 API**

DeepSeek 是深度求索公司发布的大语言模型系列，在中文理解与生成方面表现优异，且通过 OpenAI 兼容接口提供服务，降低了开发者的接入成本。本系统通过 OpenAI Python SDK 调用 DeepSeek API，调用流程为：确定用户选择的 AI 模型和 API Key（优先使用用户自定义配置，未配置时回退到系统环境变量中配置的默认 API Key）→ 构造 System Prompt（角色定义 + 行为约束 + 输出格式要求）和 User Prompt（任务描述 + 上下文数据）→ 通过 OpenAI SDK 发起 Chat Completion 请求 → 解析返回的 JSON 响应 → 执行业务逻辑。

**Prompt Engineering 应用**

Prompt Engineering（提示工程）是本系统 AI 功能的核心设计环节。系统针对不同场景设计了专门的 System Prompt，核心设计策略包括：

（1）**角色定义**：为每种 AI 功能定义明确的专家角色，如面试出题场景定义为"顶尖公司的资深技术面试官，以提问精准、深入、专业著称"，报告评估场景定义为"顶级的职业规划师和面试分析专家，拥有多年的HR和技术面试官经验"，通过角色锚定提升输出质量。

（2）**意图分类与行为路由**：在简历对话场景中，设计了包含九个维度的分类体系（intent、action、scope、section_hint、output_type、complexity、needs_clarification、language、mode），AI 每次响应用户之前先对意图进行分类，再根据分类结果选择对应的行为模式（generate 生成模式、optimize 增量优化模式、style 样式调整模式、review 审阅模式、section 区块操作模式、chat 自由对话模式），实现精准的行为控制。

（3）**增量更新策略**：在简历优化模式下，AI 只返回需要修改的内容部分（增量 patch），不重写整份简历的全文。这种策略显著降低了每次请求的 Token 消耗（特别是输出 Token），同时避免了不相关内容的意外修改。

（4）**结构化 JSON 输出**：所有 AI Prompt 均要求 AI 返回符合预定义 Schema 的 JSON 格式响应，包括字段名、类型和取值范围，确保后端能够可靠地解析 AI 输出并执行对应的业务逻辑。

**模型选型理由**

选择 DeepSeek 而非 GPT-4 的主要考量：第一，DeepSeek 在中文 NLP 任务上的表现与 GPT-4 差距不大，但 API 调用成本显著更低；第二，DeepSeek 的 OpenAI 兼容接口使得系统在需要时可以平滑切换到其他兼容的模型提供商（如智谱 GLM、月之暗面 Moonshot 等），只需修改 API Base URL 和 API Key，无需改动 Prompt 和业务代码；第三，DeepSeek 对 Prompt Engineering 技术（角色扮演、结构化输出、思维链推理等）的支持良好，满足本系统的功能需求。

DeepSeek 的主要局限性在于：对超长上下文（超过 32K Token）的支持不如 GPT-4 Turbo（128K）；英文生成能力在某些场景下不如 GPT-4 自然；不支持多模态（图像识别等）。

### 2.5 面部识别与语音识别

**face-api.js 面部表情识别**

face-api.js 是一个基于 TensorFlow.js Core 的浏览器端人脸识别 JavaScript 库，实现了 Face Detection、Face Landmark Detection、Face Recognition 和 Face Expression Recognition 四大功能。该库无需后端服务器支持，所有计算均在用户的浏览器中完成，隐私性良好。

本系统使用 TinyFaceDetector（轻量级人脸检测模型，在精度和性能之间取得平衡）和 FaceExpressionNet（情绪分类模型，输出七种基础情绪的概率分数：中性 Neutral、开心 Happy、悲伤 Sad、惊讶 Surprised、恐惧 Fearful、厌恶 Disgusted、愤怒 Angry）。实现流程为：使用 Composables 封装识别逻辑 → 初始化时异步加载模型文件 → 在面试过程中以 1 秒为间隔通过 requestAnimationFrame 循环调用 → 从 HTML5 video 元素捕获摄像头帧 → 调用 faceapi.detectSingleFace() 检测画面中的人脸 → 提取情绪分数 → 将分数和数据存入面试题目的分析数据数组中 → 前端同步渲染实时情绪面板。

face-api.js 的局限性在于：模型文件较大（总计约 5-10 MB），首次加载耗时较长；检测精度受光线条件、摄像头质量、人脸角度等因素影响较大；不提供身份识别或活体检测功能；对移动端设备的计算资源消耗较大。

**Web Speech API 语音识别**

Web Speech API 是 W3C 标准中定义的浏览器原生语音接口，由 SpeechRecognition（语音识别）和 SpeechSynthesis（语音合成）两部分组成。SpeechRecognition 接口调用操作系统的语音识别引擎（Windows 下为 Cortana 引擎，macOS 下为 Siri 引擎，Chrome 浏览器使用 Google 云端语音服务），将用户语音实时转录为文本。

系统选择 Web Speech API 而非商业语音识别服务（如讯飞、阿里云 ASR）的原因是：Web Speech API 为浏览器原生 API，无需额外的 API Key 或付费，部署简单；在安静环境下中文普通话的识别准确率可满足面试场景需求；无需后端代理或上传音频文件，有利于保护用户隐私。

实现方式为通过 Composables 封装识别逻辑：检测浏览器是否支持 SpeechRecognition 或 webkitSpeechRecognition → 创建识别实例，配置为中文连续识别模式 → 通过 onresult 事件获取实时转录结果 → 累积转录文本由父组件管理（避免 composable 内部累积导致的重复追加问题）→ 调用 start()/stop() 控制录制状态。

Web Speech API 的局限性在于：不同浏览器和操作系统间的识别准确率和行为存在差异；需要网络连接（Chrome 的语音识别在云端执行）；不支持自定义热词或专业术语的识别优化；在嘈杂环境下准确率显著下降。

### 2.6 实时通信技术

**SSE（Server-Sent Events）**

SSE 是一种基于 HTTP 协议的服务器向客户端单向推送数据的技术。客户端通过创建 EventSource 对象建立与服务器的长连接，服务器通过设置 Content-Type 为 text/event-stream 保持连接开启并持续发送数据块。SSE 协议内置了自动重连机制（连接断开后客户端自动重新建立连接）、事件 ID（用于断点续传）和事件类型（允许在同一条连接中区分不同类型的消息）。

在本系统的面试场景中，当用户完成一轮答题后，AI 需要生成追问或反馈内容。由于大模型 API 调用通常需要数秒时间，且内容的生成是逐步完成的，使用 SSE 可以逐步将生成的内容推送给前端，使用户在等待过程中能够看到 AI 正在"打字"的效果，提升交互体验。

选择 SSE 而非 WebSocket 用于面试追问的原因是：面试追问场景是单向的服务器→客户端推送（AI 生成内容推送给用户），SSE 的简单实现（标准 HTTP，无需特殊协议升级）和在经过代理/负载均衡器时的良好兼容性比 WebSocket 更适合该场景。

**WebSocket 与 Django Channels**

WebSocket 是一种在单个 TCP 连接上进行全双工通信的协议，由 IETF 标准化为 RFC 6455。与 HTTP 的请求-响应模式不同，WebSocket 连接建立后，客户端和服务器都可以在任何时间主动向对方发送数据，大大减少了通信开销和延迟。

Django Channels 是 Django 官方支持的异步通信扩展，将 Django 从传统的同步 HTTP 请求-响应模式扩展为支持 WebSocket、聊天协议、IoT 协议等异步通信协议。其核心架构由三部分组成：Interface Server（Daphne，处理 WebSocket 连接和协议协商）、Channel Layer（基于 Redis 实现，负责多进程/多实例间消息路由）以及 Consumer（类似 Django View 的异步处理单元，处理 WebSocket 连接生命周期和消息收发）。

本系统中，WebSocket 通过 ChatConsumer 实现 AI 对话和用户聊天的双向实时通信。Consumer 生命周期包括：connect（通过 JWT 认证建立连接，根据对话双方用户 ID 生成房间组名并加入 Redis Channel Layer 房间组）→ receive（根据消息类型分支处理：chat_message 文本消息的持久化与广播、typing_indicator 正在输入状态的转发、read_messages 已读回执的批量更新）→ disconnect（离开房间组并释放连接）。

Redis Channel Layer 是实现 WebSocket 跨进程通信的关键：当多个 Django 进程（或服务器）实例运行时，一个用户可能连接在进程 A 上，而目标用户连接在进程 B 上。Redis Channel Layer 通过 Pub/Sub 机制实现跨进程消息路由——进程 A 收到消息后通过 Redis 发布到房间组，进程 B 收到 Redis 通知后推送给对应的 WebSocket 客户端。

**SSE 与 WebSocket 两种技术选型对比**

SSE 的优势在于实现简单、基于标准 HTTP 协议无需特殊中间件支持、自动重连内置、适合服务器到客户端的单向数据推送。WebSocket 的优势在于全双工双向通信、单连接复用效率高、适合需要客户端频繁主动发送数据的场景。本系统根据业务场景需求分别选用两种技术：面试追问推送使用 SSE，AI 对话与用户聊天使用 WebSocket，充分发挥各自优势。

### 2.7 文档解析与 PDF 导出技术

**PaddleOCR 光学字符识别**

PaddleOCR 是百度基于 PaddlePaddle 深度学习框架开发的开源 OCR（光学字符识别）工具包，支持文字检测、文字识别、方向分类三大核心任务，在中文文本识别任务中性能领先。本系统使用 PaddleOCR 的单例模式实例化，配置为使用方向分类器（use_angle_cls=True）以处理旋转文本，语言模式为中文（lang='ch'），不使用 GPU 加速（开发环境兼容性考虑）。

对于 PDF 文件的 OCR 处理流程为：使用 pdf2image 库将 PDF 逐页转换为 JPEG 图片（200 DPI）→ 将每页图片写入临时文件 → 调用 PaddleOCR 的 ocr() 方法依次识别每页文字 → 过滤置信度低于 0.5 的低质量识别结果 → 合并各页文本为最终结果。对于单张图片的处理则直接调用 OCR 接口，无需 pdf2image 转换步骤。

PaddleOCR 在本系统中的局限性在于：对多栏布局和图文混合排版的复杂简历，文本检测框的排序算法可能出现偏差；基于 pyclipper 和 opencv 的检测模型对低分辨率图片的文本召回率不足；PP-OCR 系列的模型参数量较大，在无 GPU 环境下的推理速度较慢。

**Electron PDF 导出**

Electron 是 GitHub 开发的跨平台桌面应用框架，基于 Chromium 渲染引擎和 Node.js 运行时，使 Web 开发者能够使用 HTML、CSS 和 JavaScript 构建桌面应用。本系统利用 Electron 的隐藏 BrowserWindow 功能构建了一个独立的 PDF 生成微服务。

PDF 导出流程为：前端将简历数据（Markdown 内容 + 主题 CSS + 自定义 CSS）渲染为完整的 HTML 字符串 → 通过 HTTP POST 请求发送至本地 Electron 微服务（端口 9999）→ 微服务将 HTML 写入临时文件 → 隐藏的 BrowserWindow 加载该 file:// URL → 轮询检测 .resume-document 元素的渲染完成状态 → 调用 webContents.printToPDF() 方法生成 PDF，设置页面尺寸为 A4（210000 × 297000 微米）、自定义边距、显示页眉（简历名称）和页脚（页码 / 总页数）→ 返回 PDF 二进制数据 → 清理临时文件 → 前端通过 Blob URL 触发浏览器下载。

选择 Electron printToPDF 而非前端方案（如 html2canvas + jsPDF）的核心原因是：Chromium 的 printToPDF 原生支持 CSS 分页属性（page-break-before、page-break-after、@page 规则），能够正确处理 A4 纸张尺寸下的内容分页，而前端方案在分页精度、字体渲染和 CSS 高级特性支持方面均有较大差距。

选择独立微服务架构（而非完全集成在 Django 后端中）的考量是：Electron 进程需要 Chromium 运行时环境，内存占用较大（约 150-300 MB），将其作为独立微服务运行可避免占用 Django Web 进程的内存资源，同时支持按需启动和独立扩展。
