# AInterview 平台——AI 驱动的全流程求职赋能平台

---

## 摘要

当前大学生就业市场竞争日益激烈，应届毕业生在简历撰写和面试表现两大核心环节面临突出问题：简历难以凸显个人核心竞争力，面试因紧张与技巧不足导致发挥失常。线下专业求职指导成本高昂，难以满足应届生即时性、个性化的指导需求。针对上述问题，本文设计并实现了一款名为 AInterview 的 AI 驱动全流程求职赋能 Web 平台。

系统采用前后端分离的 B/S 架构：前端基于 Vue3 框架与 Element Plus 组件库构建用户界面，集成 face-api.js 面部表情识别库与浏览器原生 Web Speech API 实现面试过程中的情绪监测与语音转文字；后端基于 Django 框架与 Django REST Framework 开发 RESTful API，集成 DeepSeek 大语言模型实现 AI 面试出题、追问、反馈与报告生成，集成 PaddleOCR 引擎实现简历文件的OCR解析。系统采用 MySQL 作为关系型数据库，Redis 提供缓存服务与实时通信 Channel Layer，RabbitMQ 作为 Celery 异步任务队列的消息代理。实时通信方面，面试答题环节采用 SSE（Server-Sent Events）实现 AI 流式追问推送，AI 对话与用户聊天环节采用 WebSocket（Django Channels）实现双向实时通信。简历 PDF 导出功能通过 Electron 无头浏览器窗口配合 Chromium printToPDF 引擎实现 A4 精确分页输出。

经本地开发环境测试，系统已完成 AI 模拟面试、智能评估报告生成、简历智能生成与管理、操作日志、AI 参数配置等核心功能的端到端闭环。测试结果表明，系统能够实现基于岗位的 AI 动态出题、流式追问、面部表情实时分析、多维度评估报告异步生成、简历文件 OCR 解析与 AI 对话式生成、A4 PDF 导出等功能。同时，本文对 OCR 解析精度、AI 接口调用延迟、面部识别兼容性等现有不足进行了分析并提出了改进方案。

**Keywords:** AI Interview, Django REST Framework, Vue3, DeepSeek, face-api.js

## 第一章 绪论

### 1.1 研究背景与意义

近年来，我国高等教育毕业生人数持续高位运行，就业市场竞争压力不断增大。据统计，2025 届全国普通高校毕业生规模已突破 1170 万人，创历史新高。在如此激烈的求职环境中，应届毕业生普遍缺乏系统的求职实战训练，在两大核心环节存在显著短板：其一，简历撰写方面，多数毕业生难以准确把握企业用人需求，简历内容往往流于表面，无法有效凸显个人核心竞争力与企业岗位的匹配度；其二，面试表现方面，由于缺乏实战经验，毕业生在面试过程中常因紧张情绪、应答逻辑不清、表达技巧欠缺等原因导致发挥失常，错失就业机会。

与此同时，线下专业的求职指导服务收费普遍较高。一对一职业规划咨询、简历优化服务、模拟面试培训等课程的单次费用通常在数百至数千元不等，对于广大应届毕业生群体而言成本过于高昂。此外，传统线下服务受时间和空间限制，难以提供即时性响应和规模化服务。

人工智能技术的快速发展为解决上述困境提供了新的可能。以 DeepSeek 为代表的大语言模型在自然语言理解与生成方面展现出卓越能力，能够模拟专业面试官进行对话式交互，提供个性化的面试提问、追问与反馈；在简历优化方面，大模型能够根据岗位需求进行内容诊断、语言润色和结构优化。与此同时，浏览器端的面部表情识别（face-api.js）和语音识别（Web Speech API）技术的成熟，使得在前端实时采集面试者的情绪状态与语音输入成为可能，为面试评估提供了多维度数据支撑。

基于上述背景，本文设计并实现了 AInterview 平台——一款 AI 驱动的全流程求职赋能 Web 应用。平台面向高校毕业生群体，提供永久免费的 AI 模拟面试、智能评估报告生成、简历智能生成与优化等核心服务，旨在降低求职准备门槛，缩短简历制作时长，压缩面试准备周期，提升简历筛选通过率与面试成功率。

从技术实践角度看，通过本项目的全流程开发，可系统掌握 Django REST Framework 后端开发、Vue3 前端工程化设计、MySQL 数据库建模、Celery 异步任务处理、DeepSeek 大模型 API 集成、Django Channels 实时通信、Electron 桌面应用开发等核心技术，全面锻炼全栈开发与工程实践能力。

从社会价值角度看，本课题探索了 AI 技术在高校就业服务领域的落地应用，为"人工智能+教育"模式提供了具体的技术解决方案和可参考的实现路径，具有一定的实践参考价值。

### 1.2 国内外研究现状

**在线模拟面试平台**

在国内外市场，已涌现出多种在线模拟面试产品。国内方面，牛客网提供面向互联网技术岗位的在线笔试与模拟面试服务，侧重编程能力的自动化评测；赛码网聚焦于大型企业的校招在线笔试环节，面试模拟功能相对有限。国外方面，HireVue 是一家知名的 AI 视频面试平台，通过分析候选人的视频回答中的语言内容、语音语调、面部微表情等多维度信息给出评估分数，已被联合利华、希尔顿等大型企业采用；Yobs 同样提供异步视频面试服务，通过 AI 分析候选人的沟通能力、性格特质等软技能。

然而，上述产品存在三方面局限：第一，多数产品面向企业端收费，个人用户使用成本高或功能受限；第二，功能多为预先录制视频的单向评估，缺乏 AI 实时追问的交互式面试体验；第三，部分产品仅覆盖面试环节，未能与简历优化、求职数据分析等上下游环节形成闭环。

**AI 辅助简历工具**

在简历优化领域，国内外出现了多款 AI 辅助工具。国内方面，超级简历、五百丁等平台提供了在线简历编辑和模板选择功能，部分产品开始引入 AI 评分和关键词优化功能；猎聘、BOSS 直聘等招聘平台也推出了基于 AI 的简历优化建议。国外方面，Zety、Resume.io、Kickresume 等平台提供了丰富的简历模板和 AI 内容建议功能；Rezi 则专注于 ATS（Applicant Tracking System，求职者追踪系统）优化，帮助求职者制作更易被企业筛选系统识别的简历。

现有工具的主要不足在于：AI 诊断功能多停留在关键词匹配的浅层次分析，缺乏对简历内容与 JD（Job Description，岗位描述）之间深度语义匹配的评估；部分工具采用全量重写的生成方式，无法实现增量式的精细化优化，且Token消耗量较大。

**面部识别技术在面试评估中的应用**

将面部表情识别技术应用于面试评估是近年来的研究热点。学术界的研究主要集中在利用深度卷积神经网络（如 MobileNet、ResNet 等）对面部关键点进行定位并分类情绪状态。在工程应用层面，face-api.js 是基于 TensorFlow.js 的浏览器端人脸识别库，通过 TinyFaceDetector 进行人脸检测、FaceExpressionNet 进行情绪分类，支持中性、开心、悲伤、惊讶、恐惧、厌恶、愤怒七种基础情绪的实时识别，为前端集成提供了低门槛的解决方案。

现有的面部识别面试产品（如 HireVue）将面部表情作为整体评分的一个维度，但其算法存在争议：不同种族、性别、光线条件下的表现差异较大，且情绪与面试能力之间的因果关系尚缺乏充分验证。国内将面部识别应用于模拟面试的产品较少，且多以单机软件形式存在，浏览器端的 Web 集成方案尚不成熟。

**现有方案的不足与本文切入点**

综合上述分析，现有方案存在以下不足：（1）缺乏面试+简历+数据分析的全流程一体化整合平台，求职者在不同工具间切换效率低；（2）多数产品以企业付费为导向，个人免费使用体验有限；（3）AI 交互以单向评估为主，缺乏深层追问和对话式交互；（4）技术栈以 Java 或云端 API 为主，鲜有采用 Python Django + Vue3 开源全栈方案的产品，学术研究的可复现性不足。

本文的研究切入点在于：构建一个面向个人用户的免费全流程求职赋能平台，整合 AI 模拟面试（含面部表情分析和语音识别）、智能评估报告、AI 对话式简历生成与诊断、操作日志与成长看板等模块于一体，采用开源技术栈实现，探索 AI 技术在高校就业服务中的综合应用。

### 1.3 课题研究内容

本文的主要研究内容包括以下四个方面：

（1）**AI 模拟面试系统**：研究基于大语言模型的动态面试出题策略，实现根据目标岗位、简历背景和面试难度自动生成面试题目；研究 SSE 流式推送技术用于 AI 追问场景；研究浏览器端面部表情实时识别与语音转文字技术的集成方法；研究面试会话状态管理、中断恢复等工程实现。

（4）**辅助功能模块**：研究操作日志的跨表数据聚合与可视化展示；研究 Django Channels 的 WebSocket 实时通信在 AI 对话与用户聊天场景中的应用。

## 第二章 相关技术与理论

### 2.1 前端技术

**Vue3 框架与 Vite 构建工具**

Vue3 是 Vue.js 框架的第三个大版本，于 2020 年正式发布。其核心改进在于引入了基于 Proxy 的响应式系统，替代了 Vue2 中基于 Object.defineProperty 的实现，解决了后者在数组变更检测和对象属性动态添加方面的局限。Vue3 的 Composition API 提供了比 Options API 更灵活的代码组织方式，通过组合式函数（Composables）实现逻辑复用，特别适用于中大型单页应用的开发。本系统中，面部表情识别（useFaceApi）、语音识别（useSpeechRecognition）、TTS 语音合成（useTTS）、PDF 导出（useExport）、简历渲染（useResumeRenderer）等核心功能均以 Composables 形式封装，实现了业务逻辑与组件视图的分离。

Vite 是由 Vue.js 作者尤雨溪开发的新一代前端构建工具，利用浏览器原生 ES Module 支持实现了开发环境下的秒级热更新，显著提升了开发体验。在生产环境下，Vite 基于 Rollup 进行打包，输出高度优化的静态资源。

**Element Plus 组件库**

Element Plus 是 Element UI 的 Vue3 适配版本，提供了按钮、表单、表格、对话框、消息提示等丰富的 UI 组件。系统选择 Element Plus 作为基础组件库，主要考虑其与 Vue3 的深度兼容、完善的中文文档以及活跃的社区维护。在样式方面，系统基于 DESIGN.md 设计规范对 Element Plus 默认样式进行了品牌化定制，使用 CSS 变量统一管理颜色、字体和间距体系，并通过 SCSS 变量覆盖实现了与品牌视觉风格的对齐。

**TypeScript 类型系统**

TypeScript 是微软开发的 JavaScript 超集，增加了静态类型检查功能。系统全部前端代码采用 TypeScript 编写，通过接口（interface）和类型别名（type）定义了 API 响应数据、通知类型、操作日志、简历内容等核心数据结构，在编译阶段即可捕获大量潜在的类型错误。

**Pinia 状态管理**

Pinia 是 Vue3 官方推荐的状态管理库，替代了 Vue2 时代的 Vuex。Pinia 采用组合式 API 风格定义 Store，支持 TypeScript 类型推导，去除了 Mutation 概念，简化了状态管理流程。系统使用 Pinia 管理用户认证状态、操作日志、聊天消息、简历编辑状态、AI 设置等全局共享数据，通过 defineStore 创建的 Store 模块在组件中按需引用。

### 2.2 后端技术

**Django 框架**

Django 是一个由 Python 编写的高级 Web 框架，遵循 MVT（Model-View-Template）设计模式和" batteries-included"（内置电池）理念。Django 内置了 ORM（对象关系映射）、身份认证系统、管理后台、表单处理、模板引擎、中间件等全套 Web 开发基础设施，使开发者能够快速构建功能完善的 Web 应用。

选择 Django 而非 Java Spring Boot 的主要考量是：其一，Python 是 AI/机器学习生态的核心语言，直接使用 Django 调用 DeepSeek API、集成 PaddleOCR 等 AI 相关库更为自然，无需维护跨语言调用层；其二，Django 的 ORM 通过 Python 类直接定义数据模型，迁移管理（Migrations）内置于框架中，开发效率更高；其三，Django 的管理后台（Admin）功能强大，通过简单的注册代码即可为管理员用户生成完整的 CRUD 界面，适合本系统的后台管理需求。

**Django REST Framework（DRF）**

Django REST Framework 是 Django 生态中最成熟的 RESTful API 开发工具包。其核心组件包括：Serializer（序列化器，将模型实例与 JSON 之间互相转换）、ViewSet（视图集，将一组 RESTful 动作封装为单一类）、Router（路由器，自动生成 URL 配置）以及认证、权限、节流、分页、过滤等可插拔的中间组件。

本系统中，所有 API 接口均通过 DRF 开发，配置了全局 JWT 认证、标准分页（每页 20 条）、基于 drf-spectacular 的 OpenAPI Schema 自动生成等基础能力。

**Simple JWT 身份认证**

JSON Web Token（JWT）是一种轻量级的、基于 JSON 的开放标准（RFC 7519），用于在通信双方之间传递被签名的声明信息。djangorestframework-simplejwt 是 DRF 生态中最常用的 JWT 实现库。

本系统的认证流程如下：用户提交邮箱和密码至登录接口，后端通过 django-allauth 验证用户凭据，验证通过后签发一对 Token——Access Token（有效期 2 小时，用于每次 API 请求的身份验证）和 Refresh Token（有效期 7 天，用于在 Access Token 过期后获取新的 Access Token）。前端将 Token 存入 Pinia Store，通过 axios 请求拦截器自动在每次请求的 HTTP 头部附加 Authorization: Bearer <access_token>。当后端返回 401 未授权状态码时，前端自动使用 Refresh Token 换取新的 Access Token 后重试原请求，用户无感知。

相比传统的基于 Session 的认证方式，JWT 的无状态特性更适合前后端分离架构：服务器无需存储 Session 信息，水平扩展时无需 Session 同步，Token 自身包含用户身份和过期时间等声明信息。

**drf-spectacular（OpenAPI 文档）**

drf-spectacular 是 DRF 的 OpenAPI 3.0 Schema 生成工具，能够从 DRF ViewSet、Serializer 的定义中自动提取接口信息生成标准的 OpenAPI 规范文件。配合 Swagger UI 渲染，在 `/api/v1/schema/swagger-ui/` 地址提供可交互的 API 文档界面，支持在线测试接口调用。选择 drf-spectacular 而非 drf-yasg 的原因在于后者对 OpenAPI 3.0 的支持已不活跃，而 drf-spectacular 是 DRF 社区当前推荐的方案。

### 2.3 数据存储与异步任务

**MySQL 关系型数据库**

MySQL 8.0 是世界上使用最广泛的开源关系型数据库管理系统之一。选择 MySQL 作为主数据库的考量包括：成熟稳定、社区支持广泛、Django ORM 对 MySQL 有完善的支持、utf8mb4 字符集支持完整的 Unicode 编码（包括 Emoji 等 4 字节字符）。本系统使用 MySQL 8.0 存储全部业务数据，包括用户信息、面试会话、题目与回答、简历内容与结构数据、博客文章与评论、操作日志、社交互动记录等。

数据库设计中，所有表强制使用 InnoDB 存储引擎以支持事务和外键约束；对高频查询字段（如 user_id、is_read、timestamp、status）建立索引以优化查询性能；对于多对多关系（如文章的标签、对话的参与者）通过 Django ORM 自动生成的中间表管理。

**Redis 缓存与 Channel Layer**

Redis 是一个开源的高性能键值对内存数据库，支持字符串、哈希、列表、集合、有序集合等多种数据结构。本系统中 Redis 的三大用途：其一，作为 Django 缓存后端（DB 1），缓存高频查询结果，如面试参考答案（TTL 1 小时）、文章推荐列表（TTL 24 小时）；其二，作为 Celery 任务结果存储后端（DB 2），持久化异步任务的执行结果；其三，作为 Django Channels 的 Channel Layer（DB 3），在多进程/多服务器之间转发 WebSocket 消息，是 WebSocket 跨进程实时通信的关键基础设施。

**Celery 分布式任务队列与 RabbitMQ**

Celery 是一个基于分布式消息传递的异步任务队列框架，广泛应用于需要将耗时操作从 Web 请求主线程中分离出来的场景。RabbitMQ 是一个实现了 AMQP（Advanced Message Queuing Protocol，高级消息队列协议）的消息中间件，以其可靠性、灵活的路由能力和完善的持久化机制而著称。

选择 RabbitMQ 而非 Redis 作为 Celery Broker 的原因是：RabbitMQ 是 Celery 官方推荐的 Broker，提供了消息确认（Acknowledgement）、持久化和更细粒度的路由控制，在任务可靠性和生产环境稳定性方面优于 Redis。本系统中，Celery 负责三类异步任务：面试评估报告的 AI 分析与生成、定时清理超时的面试会话（每 15 分钟扫描一次，将 30 分钟以上未活动的进行中面试自动标记为已取消）、博客每日数据统计（每晚 23:50 执行）。

### 2.4 AI 大语言模型接口

**DeepSeek 大模型 API**

DeepSeek 是深度求索公司发布的大语言模型系列，在中文理解与生成方面表现优异，且通过 OpenAI 兼容接口提供服务，降低了开发者的接入成本。本系统通过 OpenAI Python SDK 调用 DeepSeek API，调用流程为：确定用户选择的 AI 模型和 API Key（优先使用用户自定义配置，未配置时回退到系统环境变量中配置的默认 API Key）→ 构造 System Prompt（角色定义 + 行为约束 + 输出格式要求）和 User Prompt（任务描述 + 上下文数据）→ 通过 OpenAI SDK 发起 Chat Completion 请求 → 解析返回的 JSON 响应 → 执行业务逻辑。

**Prompt Engineering 应用**

Prompt Engineering（提示工程）是本系统 AI 功能的核心设计环节。系统针对不同场景设计了专门的 System Prompt，核心设计策略包括：

（1）**角色定义**：为每种 AI 功能定义明确的专家角色，如面试出题场景定义为"顶尖公司的资深技术面试官，以提问精准、深入、专业著称"，报告评估场景定义为"顶级的职业规划师和面试分析专家，拥有多年的HR和技术面试官经验"，通过角色锚定提升输出质量。

（2）**意图分类与行为路由**：在简历对话场景中，设计了包含九个维度的分类体系（intent、action、scope、section_hint、output_type、complexity、needs_clarification、language、mode），AI 每次响应用户之前先对意图进行分类，再根据分类结果选择对应的行为模式（generate 生成模式、optimize 增量优化模式、style 样式调整模式、review 审阅模式、section 区块操作模式、chat 自由对话模式），实现精准的行为控制。

（3）**增量更新策略**：在简历优化模式下，AI 只返回需要修改的内容部分（增量 patch），不重写整份简历的全文。这种策略显著降低了每次请求的 Token 消耗（特别是输出 Token），同时避免了不相关内容的意外修改。

（4）**结构化 JSON 输出**：所有 AI Prompt 均要求 AI 返回符合预定义 Schema 的 JSON 格式响应，包括字段名、类型和取值范围，确保后端能够可靠地解析 AI 输出并执行对应的业务逻辑。

**模型选型理由**

选择 DeepSeek 而非 GPT-4 的主要考量：第一，DeepSeek 在中文 NLP 任务上的表现与 GPT-4 差距不大，但 API 调用成本显著更低；第二，DeepSeek 的 OpenAI 兼容接口使得系统在需要时可以平滑切换到其他兼容的模型提供商（如智谱 GLM、月之暗面 Moonshot 等），只需修改 API Base URL 和 API Key，无需改动 Prompt 和业务代码；第三，DeepSeek 对 Prompt Engineering 技术（角色扮演、结构化输出、思维链推理等）的支持良好，满足本系统的功能需求。

DeepSeek 的主要局限性在于：对超长上下文（超过 32K Token）的支持不如 GPT-4 Turbo（128K）；英文生成能力在某些场景下不如 GPT-4 自然；不支持多模态（图像识别等）。

### 2.5 面部识别与语音识别

**face-api.js 面部表情识别**

face-api.js 是一个基于 TensorFlow.js Core 的浏览器端人脸识别 JavaScript 库，实现了 Face Detection、Face Landmark Detection、Face Recognition 和 Face Expression Recognition 四大功能。该库无需后端服务器支持，所有计算均在用户的浏览器中完成，隐私性良好。

本系统使用 TinyFaceDetector（轻量级人脸检测模型，在精度和性能之间取得平衡）和 FaceExpressionNet（情绪分类模型，输出七种基础情绪的概率分数：中性 Neutral、开心 Happy、悲伤 Sad、惊讶 Surprised、恐惧 Fearful、厌恶 Disgusted、愤怒 Angry）。实现流程为：使用 Composables 封装识别逻辑 → 初始化时异步加载模型文件 → 在面试过程中以 1 秒为间隔通过 requestAnimationFrame 循环调用 → 从 HTML5 video 元素捕获摄像头帧 → 调用 faceapi.detectSingleFace() 检测画面中的人脸 → 提取情绪分数 → 将分数和数据存入面试题目的分析数据数组中 → 前端同步渲染实时情绪面板。

face-api.js 的局限性在于：模型文件较大（总计约 5-10 MB），首次加载耗时较长；检测精度受光线条件、摄像头质量、人脸角度等因素影响较大；不提供身份识别或活体检测功能；对移动端设备的计算资源消耗较大。

**Web Speech API 语音识别**

Web Speech API 是 W3C 标准中定义的浏览器原生语音接口，由 SpeechRecognition（语音识别）和 SpeechSynthesis（语音合成）两部分组成。SpeechRecognition 接口调用操作系统的语音识别引擎（Windows 下为 Cortana 引擎，macOS 下为 Siri 引擎，Chrome 浏览器使用 Google 云端语音服务），将用户语音实时转录为文本。

系统选择 Web Speech API 而非商业语音识别服务（如讯飞、阿里云 ASR）的原因是：Web Speech API 为浏览器原生 API，无需额外的 API Key 或付费，部署简单；在安静环境下中文普通话的识别准确率可满足面试场景需求；无需后端代理或上传音频文件，有利于保护用户隐私。

实现方式为通过 Composables 封装识别逻辑：检测浏览器是否支持 SpeechRecognition 或 webkitSpeechRecognition → 创建识别实例，配置为中文连续识别模式 → 通过 onresult 事件获取实时转录结果 → 累积转录文本由父组件管理（避免 composable 内部累积导致的重复追加问题）→ 调用 start()/stop() 控制录制状态。

Web Speech API 的局限性在于：不同浏览器和操作系统间的识别准确率和行为存在差异；需要网络连接（Chrome 的语音识别在云端执行）；不支持自定义热词或专业术语的识别优化；在嘈杂环境下准确率显著下降。

### 2.6 实时通信技术

**SSE（Server-Sent Events）**

SSE 是一种基于 HTTP 协议的服务器向客户端单向推送数据的技术。客户端通过创建 EventSource 对象建立与服务器的长连接，服务器通过设置 Content-Type 为 text/event-stream 保持连接开启并持续发送数据块。SSE 协议内置了自动重连机制（连接断开后客户端自动重新建立连接）、事件 ID（用于断点续传）和事件类型（允许在同一条连接中区分不同类型的消息）。

在本系统的面试场景中，当用户完成一轮答题后，AI 需要生成追问或反馈内容。由于大模型 API 调用通常需要数秒时间，且内容的生成是逐步完成的，使用 SSE 可以逐步将生成的内容推送给前端，使用户在等待过程中能够看到 AI 正在"打字"的效果，提升交互体验。

选择 SSE 而非 WebSocket 用于面试追问的原因是：面试追问场景是单向的服务器→客户端推送（AI 生成内容推送给用户），SSE 的简单实现（标准 HTTP，无需特殊协议升级）和在经过代理/负载均衡器时的良好兼容性比 WebSocket 更适合该场景。

**WebSocket 与 Django Channels**

WebSocket 是一种在单个 TCP 连接上进行全双工通信的协议，由 IETF 标准化为 RFC 6455。与 HTTP 的请求-响应模式不同，WebSocket 连接建立后，客户端和服务器都可以在任何时间主动向对方发送数据，大大减少了通信开销和延迟。

Django Channels 是 Django 官方支持的异步通信扩展，将 Django 从传统的同步 HTTP 请求-响应模式扩展为支持 WebSocket、聊天协议、IoT 协议等异步通信协议。其核心架构由三部分组成：Interface Server（Daphne，处理 WebSocket 连接和协议协商）、Channel Layer（基于 Redis 实现，负责多进程/多实例间消息路由）以及 Consumer（类似 Django View 的异步处理单元，处理 WebSocket 连接生命周期和消息收发）。

本系统中，WebSocket 通过 ChatConsumer 实现 AI 对话和用户聊天的双向实时通信。Consumer 生命周期包括：connect（通过 JWT 认证建立连接，根据对话双方用户 ID 生成房间组名并加入 Redis Channel Layer 房间组）→ receive（根据消息类型分支处理：chat_message 文本消息的持久化与广播、typing_indicator 正在输入状态的转发、read_messages 已读回执的批量更新）→ disconnect（离开房间组并释放连接）。

Redis Channel Layer 是实现 WebSocket 跨进程通信的关键：当多个 Django 进程（或服务器）实例运行时，一个用户可能连接在进程 A 上，而目标用户连接在进程 B 上。Redis Channel Layer 通过 Pub/Sub 机制实现跨进程消息路由——进程 A 收到消息后通过 Redis 发布到房间组，进程 B 收到 Redis 通知后推送给对应的 WebSocket 客户端。

**SSE 与 WebSocket 两种技术选型对比**

SSE 的优势在于实现简单、基于标准 HTTP 协议无需特殊中间件支持、自动重连内置、适合服务器到客户端的单向数据推送。WebSocket 的优势在于全双工双向通信、单连接复用效率高、适合需要客户端频繁主动发送数据的场景。本系统根据业务场景需求分别选用两种技术：面试追问推送使用 SSE，AI 对话与用户聊天使用 WebSocket，充分发挥各自优势。

### 2.7 文档解析与 PDF 导出技术

**PaddleOCR 光学字符识别**

PaddleOCR 是百度基于 PaddlePaddle 深度学习框架开发的开源 OCR（光学字符识别）工具包，支持文字检测、文字识别、方向分类三大核心任务，在中文文本识别任务中性能领先。本系统使用 PaddleOCR 的单例模式实例化，配置为使用方向分类器（use_angle_cls=True）以处理旋转文本，语言模式为中文（lang='ch'），不使用 GPU 加速（开发环境兼容性考虑）。

对于 PDF 文件的 OCR 处理流程为：使用 pdf2image 库将 PDF 逐页转换为 JPEG 图片（200 DPI）→ 将每页图片写入临时文件 → 调用 PaddleOCR 的 ocr() 方法依次识别每页文字 → 过滤置信度低于 0.5 的低质量识别结果 → 合并各页文本为最终结果。对于单张图片的处理则直接调用 OCR 接口，无需 pdf2image 转换步骤。

PaddleOCR 在本系统中的局限性在于：对多栏布局和图文混合排版的复杂简历，文本检测框的排序算法可能出现偏差；基于 pyclipper 和 opencv 的检测模型对低分辨率图片的文本召回率不足；PP-OCR 系列的模型参数量较大，在无 GPU 环境下的推理速度较慢。

**Electron PDF 导出**

Electron 是 GitHub 开发的跨平台桌面应用框架，基于 Chromium 渲染引擎和 Node.js 运行时，使 Web 开发者能够使用 HTML、CSS 和 JavaScript 构建桌面应用。本系统利用 Electron 的隐藏 BrowserWindow 功能构建了一个独立的 PDF 生成微服务。

PDF 导出流程为：前端将简历数据（Markdown 内容 + 主题 CSS + 自定义 CSS）渲染为完整的 HTML 字符串 → 通过 HTTP POST 请求发送至本地 Electron 微服务（端口 9999）→ 微服务将 HTML 写入临时文件 → 隐藏的 BrowserWindow 加载该 file:// URL → 轮询检测 .resume-document 元素的渲染完成状态 → 调用 webContents.printToPDF() 方法生成 PDF，设置页面尺寸为 A4（210000 × 297000 微米）、自定义边距、显示页眉（简历名称）和页脚（页码 / 总页数）→ 返回 PDF 二进制数据 → 清理临时文件 → 前端通过 Blob URL 触发浏览器下载。

选择 Electron printToPDF 而非前端方案（如 html2canvas + jsPDF）的核心原因是：Chromium 的 printToPDF 原生支持 CSS 分页属性（page-break-before、page-break-after、@page 规则），能够正确处理 A4 纸张尺寸下的内容分页，而前端方案在分页精度、字体渲染和 CSS 高级特性支持方面均有较大差距。

选择独立微服务架构（而非完全集成在 Django 后端中）的考量是：Electron 进程需要 Chromium 运行时环境，内存占用较大（约 150-300 MB），将其作为独立微服务运行可避免占用 Django Web 进程的内存资源，同时支持按需启动和独立扩展。

## 第三章 需求分析

### 3.1 可行性分析

**技术可行性**

前端方面，Vue3 框架与 Element Plus 组件库生态成熟，社区活跃，能够快速构建交互良好的单页应用。face-api.js 在浏览器端实现了面部表情识别，Web Speech API 为浏览器原生接口，均无需服务端参与即可完成情绪与语音数据的采集，隐私性良好。

后端方面，Django 4.x 与 Django REST Framework 是 Python 生态中成熟稳定的 Web 开发框架组合，Celery + RabbitMQ 的异步任务方案在工业界有大量成功案例。AI 能力方面，DeepSeek 大模型通过 OpenAI 兼容接口提供服务，接入成本低；PaddleOCR 是百度开源的中文 OCR 引擎，在中文文本识别任务中性能优秀。上述技术栈均为开源产品，许可证友好，不存在商用授权风险。开发者在本科阶段已通过课程学习和项目实践掌握了 Python Web 开发、Vue 前端开发和数据库设计等相关技能，具备完成本项目的技术能力。

**经济可行性**

系统全部采用开源技术栈，无软件授权费用。DeepSeek API 的调用成本显著低于 GPT-4 等同类产品（以 DeepSeek-V3 为例，输入价格约为 GPT-4o 的十分之一），且系统支持用户配置个人 API Key，将部分 AI 调用成本转移至用户侧。其他基础设施（MySQL、Redis、RabbitMQ）均为免费开源产品。开发环境使用本地机器即可运行，无需云服务器。总体而言，开发与运行成本可控。

**操作可行性**

系统采用 B/S 架构，用户通过浏览器即可访问全部功能，无需安装客户端软件。界面采用中文语言，基于 Element Plus 组件库构建，交互模式与主流 Web 应用一致，降低用户学习成本。目标用户群体（高校应届毕业生）具备基本的计算机操作能力和浏览器使用经验，能够无障碍使用本系统的各项功能。

### 3.2 用户角色分析

本系统包含两类用户角色：

**（1）求职者（Candidate）**

求职者是系统的核心用户群体，主要使用场景包括：注册登录后进入仪表盘查看求职数据概览；创建或上传简历，使用 AI 对话式生成或优化简历内容，导出 A4 PDF；选择目标岗位和难度发起 AI 模拟面试，在面试过程中开启摄像头进行面部表情监测和语音录入，回答 AI 生成的面试题目并接收实时追问；面试结束后查看智能评估报告，了解综合评分、能力雷达图、情绪波动分析和逐题反馈；使用简历诊断功能输入目标岗位 JD，获取简历-岗位匹配分析报告；在通知中心查看操作日志，追踪求职活动历史；在设置页面配置 AI 模型和 API Key。

**（2）管理员（Admin）**

管理员通过 Django 内置管理后台（/admin/）进行系统运维，主要职责包括：管理 AI 模型配置（添加新的模型提供商、设置 API Base URL、启用/禁用模型）；维护行业分类与面试岗位数据；管理用户账号（查看、禁用、删除）；查看系统全局数据。

### 3.3 功能性需求

根据用户角色的使用场景分析，系统共划分为五大核心功能模块：

**（1）用户认证与个人信息模块**

用户通过邮箱和密码注册账号，登录后获取 JWT 双 Token（Access Token + Refresh Token）。系统支持 Token 自动续期，用户无感知。个人中心支持修改用户名、手机号、头像等个人信息，以及修改登录密码。

**（2）AI 模拟面试模块**

面试创建：用户选择目标面试岗位和难度等级（简单/中等/困难），设定题目数量，可选关联已有简历以提供个性化出题背景。系统检查是否有未完成的面试并提示恢复或放弃。

面试答题：系统调用 DeepSeek API 动态生成首道面试题目。用户通过语音或键盘输入回答，系统收集面部表情数据（以 1 秒为间隔）。提交回答后，AI 自动分析答案并生成即时反馈，随后通过 SSE 流式推送下一道题目的追问。答题过程中可查看 AI 参考答案（带 Redis 缓存，1 小时有效）。

面试结束：用户完成所有题目或主动结束面试后，系统异步生成综合评估报告。

面部表情监测：调用浏览器摄像头，通过 face-api.js 的 TinyFaceDetector 和 FaceExpressionNet 模型实时检测人脸并识别七种基础情绪（中性、开心、悲伤、惊讶、恐惧、厌恶、愤怒），将情绪时间序列数据附加到每道题目的分析数据中。

语音识别：调用浏览器 Web Speech API 进行中文连续语音识别，将用户语音实时转录为文本填入答题框。

**（3）智能评估报告模块**

报告内容：综合面试评分（百分制）、能力维度雷达图（含沟通表达、逻辑思维、专业知识、应变能力、岗位匹配度五个维度）、面试过程情绪波动分析、基于 STAR 法则的逐题反馈与改进建议。

报告生成机制：通过 Celery 异步任务在后台调用 AI 完成分析，不阻塞用户的主请求流程。生成的报告以 JSON 格式存储在数据库中，前端负责可视化渲染。

**（4）简历管理模块**

文件上传与 OCR 解析：支持上传 PDF、PNG、JPG 格式的简历文件。PDF 文件通过 pdf2image 转换为图片后调用 PaddleOCR 逐页识别文本；图片文件直接调用 OCR 识别。解析结果过滤低置信度文本后存储为简历内容。

在线简历创建：用户可手动创建空白简历，通过结构化表单填写教育经历、工作经历、项目经历、专业技能等信息。

AI 对话式简历生成：用户通过三步引导（输入姓名、岗位、工作年限、关键词）获取 AI 生成的初始简历 JSON，进入对话式编辑界面。AI 根据九维度意图分类体系（intent、action、scope、section_hint、output_type、complexity、needs_clarification、language、mode）自动识别用户输入意图，选择对应的行为模式（generate 生成、optimize 增量优化、style 样式调整、review 审阅、section 区块操作、chat 自由对话），返回增量式更新指令（instructions），前端根据指令更新简历的指定区域而非全量替换。对话过程通过 WebSocket（Django Channels）实现双向实时通信。

简历模板与样式：系统提供多种预设模板，采用双层 CSS 架构——基础布局 CSS（固定，控制各区块的排版和分页行为）+ 主题 CSS（可切换，控制字体、颜色、间距等视觉风格）+ 用户自定义 CSS（最高优先级覆盖），实现模板与内容的分离。

简历诊断：用户选择简历并输入目标岗位 JD，AI 从技能匹配、经验匹配、关键词覆盖、格式质量、改进建议五个维度进行分析，生成匹配度评分。

PDF 导出：基于 Electron 隐藏 BrowserWindow 的 printToPDF API 实现 A4 精确分页导出，支持页面页脚（简历名称、页码、总页数）和自定义边距。

**（5）AI 参数配置与操作日志模块**

AI 参数配置：系统预置多个 AI 模型供用户选择（如 DeepSeek-V3、DeepSeek-R1 等）。用户可为每个模型配置独立的 API Key（JSON 存储），设置默认使用的模型。AI 功能调用时优先使用用户配置，未配置时回退到系统环境变量中的默认 Key。

操作日志：系统自动记录用户的关键操作（面试开始/完成/异常退出、简历导出/诊断/生成/发布、报告生成），每条日志包含操作类型、操作状态（成功/警告/错误）、关联资源类型和资源 ID、操作数据和发生时间。支持按资源类型筛选日志、单条标记已读和全部标记已读。

### 3.4 非功能性需求

**（1）性能需求**

页面首次加载时间不超过 3 秒；API 接口（不含 AI 调用）响应时间不超过 1 秒；AI 接口调用设置合理超时（面试出题 30 秒，报告生成 120 秒）；列表类接口全部实现分页（每页 20 条）。

**（2）安全性需求**

API 接口全部要求 JWT 认证，未登录用户无法访问业务数据；Access Token 有效期 2 小时，Refresh Token 有效期 7 天；用户密码经 Django 内置的 PBKDF2 哈希算法加密存储，不保存明文；前端对用户输入进行 HTML 转义，防止 XSS 攻击；数据库查询全部通过 Django ORM 的参数化查询执行，防止 SQL 注入；文件上传限制文件类型和大小（PDF/JPG/PNG，最大 10MB）；CORS 配置仅允许前端域名的跨域请求。

**（3）可用性需求**

界面为全中文，文案清晰无歧义；表单输入提供实时校验反馈和错误提示；关键操作（清空数据、重置配置、放弃面试）提供确认对话框；长时间 AI 调用显示加载进度指示，避免用户误认为系统卡死。

**（4）可维护性需求**

前后端完全分离，独立开发、构建和部署；后端通过 drf-spectacular 自动生成 OpenAPI 3.0 规范文档，配合 Swagger UI 提供可交互的 API 调试界面；前端全部采用 TypeScript，定义核心数据接口类型，编译期捕获类型错误；Vue3 Composables 封装可复用逻辑，避免组件间代码重复。

## 第四章 系统设计

### 4.1 总体架构设计

系统采用前后端分离的 B/S 架构，整体分为四层：表现层、业务逻辑层、数据层和 AI 能力层。

**表现层**：基于 Vue3 + TypeScript + Element Plus 构建的 SPA 单页应用，通过 Vite 构建工具打包为静态资源。浏览器端集成 face-api.js（面部表情识别）、Web Speech API（语音识别/合成）和 Electron 无头浏览器（PDF 导出微服务）。前端通过 HTTP RESTful API 与后端通信（面试追问使用 SSE 流式响应），通过 WebSocket 与 Django Channels 进行实时双向通信。

**业务逻辑层**：基于 Django 4.x + Django REST Framework 构建的 RESTful API 服务，负责用户认证与授权（JWT + Simple JWT）、业务逻辑处理、数据序列化与校验、API 路由分发。Celery Worker 进程负责异步执行耗时任务。Django Channels（基于 ASGI 服务器 Daphne）负责 WebSocket 连接管理和消息路由。

**数据层**：MySQL 8.0 存储全部业务数据（用户、面试、简历、报告、日志等）；Redis 承担三重职责——Django 缓存后端（DB 1）、Celery 结果存储（DB 2）、Django Channels 的 Channel Layer（DB 3）；RabbitMQ 作为 Celery 的消息代理（Broker）。

**AI 能力层**：通过 OpenAI Python SDK 统一调用 DeepSeek 等大语言模型 API，提供面试出题、答案分析、追问生成、报告评估、简历生成、JD 匹配诊断等 AI 能力。PaddleOCR 引擎提供简历文件的文字识别能力。

系统部署在 Docker 容器化环境中，由 docker-compose.yml 编排管理各服务（Django Web、Celery Worker、Celery Beat、MySQL、Redis、RabbitMQ、Nginx）的启动顺序和网络通信。

### 4.2 功能模块划分

依据 3.3 节的功能性需求分析，系统划分为六个主要功能模块：

**（1）用户认证与个人信息模块（users）**：注册、登录（JWT 双 Token 签发与刷新）、第三方 OAuth 登录、个人信息 CRUD、头像上传。

**（2）AI 模拟面试模块（interviews）**：面试会话创建与管理（含中断恢复）、面试出题与流式追问（SSE）、答题提交与即时反馈、面部表情数据采集、语音转文字、AI 参考答案查看、面试状态定时清理（Celery Beat 定时任务）。

**（3）智能评估报告模块（reports）**：面试综合评估报告生成（Celery 异步任务）、简历分析报告（JD-简历匹配）。

**（4）简历管理模块（resumes）**：文件上传与 OCR 解析（PaddleOCR）、在线简历 CRUD（结构化字段 + JSON 灵活内容）、AI 对话式简历生成与优化、简历模板管理（双层 CSS 架构）、简历诊断（JD 匹配分析）、A4 PDF 导出（Electron printToPDF 微服务）。

**（5）操作日志模块（notifications）**：操作日志自动记录、按资源类型筛选、已读/全部已读管理。

**（6）AI 参数配置模块（system）**：AI 模型 CRUD（管理员）、行业分类管理（管理员）、面试岗位管理（管理员）、用户 AI 设置（模型选择 + 多 Key 配置）。

### 4.3 核心功能流程设计

**4.3.1 AI 模拟面试流程**

用户进入面试准备页 → 选择目标岗位、难度和题目数，可选关联简历 → 系统检查是否有未完成面试，若有则提示恢复或放弃 → 用户确认后调用 AI 生成首道题目 → 面试正式开始，进入答题界面 → 对于每道题目：用户可选择开启摄像头（面部表情监测）和麦克风（语音识别），输入回答后提交 → 后端分析答案生成即时反馈，判断是否达到题目总数——若未达到则通过 SSE 流式推送下一道追问，达到则提示面试结束 → 用户确认结束面试 → 系统触发 Celery 异步任务生成综合评估报告 → 用户跳转至报告页面查看结果。

**4.3.2 AI 对话式简历生成流程**

用户进入简历生成页面 → 填写基本信息表单（姓名、目标岗位、工作年限、关键词）→ 系统调用 AI 生成初始简历 JSON → 进入对话式编辑界面，左侧为简历实时预览，右侧为 AI 对话面板 → 用户在对话输入框发送自然语言修改指令 → AI 对用户意图进行九维度分类 → 根据分类结果选择行为模式 → 返回增量更新指令（instructions，指定修改的目标区块和内容）而非全量重写 → 前端根据 instructions 精确更新 resume JSON 的对应字段 → 预览面板实时反映更新结果 → 用户可随时切换模板主题 → 完成后发布简历或导出为 A4 PDF。

**4.3.3 简历文件上传与 OCR 解析流程**

用户选择简历文件（PDF/PNG/JPG）→ 前端校验文件类型和大小 → 上传至后端 → 后端保存文件，读取文件扩展名 → 分支处理：若为 PDF，调用 pdf2image 逐页转换为 JPEG 图片（200 DPI）；若为图片，直接进入 OCR → PaddleOCR 单例实例依次处理每页图片 → 过滤置信度低于 0.5 的识别结果 → 合并各页文本为完整解析内容 → 保存至 Resume.parsed_content 字段 → 标记状态为"已解析"或"解析失败"。

### 5.2 AI 模拟面试模块实现

**5.2.1 AI 服务层设计**

面试模块的 AI 能力通过 `interviews/ai_services.py` 统一封装，提供以下核心函数：

- `generate_first_question(job_position, user, resume_text)`：根据岗位、用户信息和简历背景生成首道面试题。System Prompt 将 AI 角色定义为"顶尖公司的资深技术面试官"，要求生成与岗位高度相关的开放式行为面试题或技术情景题。

- `analyze_answer(job_position, question, answer, user)`：对用户的单题回答进行分析，返回即时反馈。反馈内容涵盖回答的优点、不足和改进建议。

- `generate_next_question_stream(job_position, history, user)`：基于历史问答记录生成追问，使用 Python Generator + yield 实现流式输出，供 SSE 逐块推送给前端。追问策略要求 AI 根据用户上一题的回答表现（回答深度、逻辑结构、技术准确性）决定追问方向——回答较好时深入追问细节，回答较弱时给予引导性提示。

- `generate_final_report(job_position, interview_history, user, resume_text)`：汇总全部问答记录和面部表情数据，生成综合评估报告。报告采用结构化 JSON 格式，包含 overall_score（综合评分）、dimensions（五维度评分）、emotion_analysis（情绪波形数据）、question_reviews（逐题 STAR 评估与改进建议）。

- `generate_reference_answer_for_question(job_position, question, user, resume_text)`：为指定题目生成 AI 参考答案，供用户在面试后对照学习。

所有 AI 调用均通过 `AIServiceHelper` 工具类实现统一的 API Key 解析（优先用户配置，回退系统默认）、模型选择和错误处理。

**5.2.2 SSE 流式追问推送实现**

与常规的 SSE 聊天场景不同，面试追问场景需要在 AI 生成追问文本的同时，将上一题的即时反馈返回给前端。系统采用自定义 HTTP Header 方案解决这一双通道问题：后端通过 `StreamingHttpResponse` 将追问文本作为流式 Body 逐块推送，同时将反馈文本经过 URL 编码后放入自定义响应头 `X-Feedback` 中。前端在接收 SSE 流的同时通过读取响应的 `X-Feedback` 头获取反馈内容，两者互不干扰。

流式追问完成后，系统将完整的追问文本持久化到 InterviewQuestion 表，确保面试状态可恢复。由于 Django 的同步 WSGI 环境本身支持 StreamingHttpResponse（单线程阻塞式流式传输），且面试追问的业务量级不需要处理数千并发连接，因此选择在 WSGI 模式下直接使用 StreamingHttpResponse 而非升级到 ASGI，降低了部署复杂度。

**5.2.3 面部表情实时监测实现**

前端通过 `composables/useFaceApi.ts` 封装面部识别逻辑。核心实现流程为：

(1) 初始化阶段，异步加载 face-api.js 的四个模型文件（TinyFaceDetector 检测模型、FaceLandmark68 关键点模型、FaceExpressionNet 表情模型、SSD MobileNet 特征提取模型），模型文件部署在前端 `public/models/` 目录下。

(2) 用户开启摄像头后，通过 `navigator.mediaDevices.getUserMedia()` 获取视频流，绑定到隐藏的 HTML5 `<video>` 元素。

(3) 在 `requestAnimationFrame` 循环中，以 1 秒为间隔（通过时间戳差值控制采样频率避免过度计算）调用 `faceapi.detectSingleFace(video, new TinyFaceDetector()).withFaceExpressions()` 方法，获取当前帧的人脸检测结果和七种情绪的概率分布。

(4) 将每帧的情绪分数和时间戳打包为 JSON 对象，追加到面试当前题目的 analysis_data 数组中。

(5) 前端实时渲染情绪面板：显示当前主导情绪（概率最高的情绪）、各情绪的概率柱状图，以及面试全程的情绪波动折线图（使用 ECharts 库）。

(6) 关闭摄像头时停止 `requestAnimationFrame` 循环，释放 `MediaStream` 轨道。

**5.2.4 语音识别实现**

前端通过 `composables/useSpeechRecognition.ts` 封装语音识别逻辑。检测浏览器是否支持 `SpeechRecognition` 或 `webkitSpeechRecognition` 接口，创建识别实例并配置为中文连续识别模式（`lang='zh-CN'`, `continuous=true`, `interimResults=true`）。通过 `onresult` 事件获取实时转录结果（`event.results` 包含 interim 临时结果和 final 最终结果），累积转录文本交由父组件管理以避免 composable 内部的重复追加问题。调用 `start()` / `stop()` 方法控制录制启停，界面通过麦克风图标状态提示用户当前录制状态。

**5.2.5 面试状态管理与定时清理**

面试会话的状态流转为：`pending → running → finished/canceled`。用户创建面试时系统在 Redis 中缓存当前会话 ID（TTL 2 小时），前端路由守卫在每次进入 Dashboard 时检查是否有未完成面试并提示用户恢复或放弃。用户主动放弃时将会话状态更新为 `canceled` 并清除 Redis 缓存。

Celery Beat 调度器每 15 分钟执行一次 `cleanup_stale_interviews` 定时任务，扫描所有状态为 `running` 且 `updated_at` 超过 30 分钟未更新的面试会话，批量标记为 `canceled`，防止因用户关闭浏览器等异常退出导致的会话泄漏。

### 5.3 智能评估报告模块实现

**5.3.1 面试综合报告**

面试结束时，前端调用 `finish` 接口触发报告生成。后端收集本次面试的全部问答记录和面部表情数据，调用 `generate_final_report` 函数。AI 综合分析以下维度：(1) 面试整体表现，给出综合评分（0-100 分）；(2) 从沟通表达、逻辑思维、专业知识、应变能力、岗位匹配度五个维度分别评分并生成雷达图数据；(3) 根据面部表情时间序列数据分析面试过程中的情绪波动趋势；(4) 对每道题目按照 STAR 法则（Situation 情境、Task 任务、Action 行动、Result 结果）逐题评估，给出改进建议。

报告数据以 JSON 格式存储在 `InterviewSession.report` 字段中。前端 `ReportDetail.vue` 页面负责将 JSON 数据渲染为可视化报告：综合评分以大号数字显示，配以圆形进度环；五维度评分使用雷达图（ECharts Radar Chart）；情绪波动使用折线图（ECharts Line Chart）；逐题反馈以折叠面板（Accordion）形式展示，每道题目展开后显示原题、用户回答、AI 评分和 STAR 改进建议。

**5.3.2 简历诊断报告**

简历诊断模块接收用户选择的简历和目标岗位 JD，调用 `analyze_resume_against_jd` 函数进行深度语义匹配分析。AI 从技能匹配度、经验匹配度、关键词覆盖、格式质量、整体建议五个维度输出分析结果，生成匹配度综合评分。每次诊断结果保存为 `ResumeAnalysisReport` 记录，用户可在历史页面查看历次诊断报告。

### 5.4 简历管理模块实现

**5.4.1 OCR 文件解析**

简历文件解析服务封装在 `resumes/services.py` 的 `extract_text_from_file` 函数中。PaddleOCR 实例采用单例模式（模块级变量 `_ocr_instance`），首次调用时初始化，后续复用，避免重复加载模型（每次初始化需 3-5 秒）。初始化参数：`use_angle_cls=True`（启用方向分类器处理旋转文本）、`lang='ch'`（中文模式）、`use_gpu=False`（开发环境兼容性）。对于 PDF 文件，通过 pdf2image 库（底层调用 poppler-utils）将 PDF 逐页转换为 JPEG 图片，分辨率设为 200 DPI（在识别精度和处理速度之间的折中选择），每页图片写入临时文件后调用 `ocr()` 方法识别；识别完成后立即清理临时文件。对于图片文件，直接调用 `ocr()` 方法。识别结果过滤置信度低于 0.5 的低质量结果，合并各页文本后返回。

**5.4.2 AI 对话式简历生成**

AI 对话式简历生成是本系统简历模块的核心创新。前后端协作流程如下：

(1) **初始生成阶段**：用户在引导页填写基本信息（姓名、目标岗位、工作年限、关键词），前端调用 `/api/v1/generate-resume/` 接口。后端 `generate_resume_by_ai` 函数构造包含格式规范和示例的 System Prompt，调用 AI 生成完整的结构化简历 JSON（包含 personal_info、summary、experiences、education、skills、projects 等区块）。

(2) **对话式编辑阶段**：用户进入双栏编辑界面——左侧为实时简历预览，右侧为 AI 对话面板。用户以自然语言发送修改指令（如"帮我把工作经历的描述改得更量化一些""使用更专业的词汇改写个人总结"）。前端通过 HTTP POST 将消息发送至 `/api/v1/generate-resume-chat/`，后端 `generate_resume_chat_response` 函数处理请求。

(3) **意图分类与增量更新**：AI 响应用户之前，首先对用户的意图进行九维度分类。分类体系包括：intent（用户想做什么）、action（对应操作类型：generate/optimize/style/review/section/chat）、scope（修改范围：全文/特定区块）、section_hint（目标区块）、output_type（输出类型）、complexity（复杂度）、needs_clarification（是否需要追问）、language（语言偏好）、mode（交互模式）。根据分类结果，AI 选择对应的行为模式并生成增量更新指令（instructions）而非全量重写简历。例如，优化模式只返回需要修改的具体字段和内容，样式调整模式只返回 CSS 变量的修改值，审阅模式只返回诊断意见不修改内容。这种增量更新策略显著降低了每次请求的 Token 消耗——实测中优化单段文字的输出 Token 仅为全量重写的 5%-15%。

(4) **前端响应式更新**：前端收到 AI 返回的 instructions 后，通过 `useResumeAI.ts` 中的 `applyInstructions` 函数精确更新 resume JSON 的对应字段，左侧预览面板实时反映更新结果，无需整页刷新。

**5.4.3 简历模板双层 CSS 架构**

简历渲染采用"模板 = 布局结构 + 视觉主题"的分层设计。布局 CSS（包含在模板的 HTML 结构中）定义各区块的排版和 CSS 分页属性（`page-break-before`、`page-break-after`、`@page`），控制内容在 A4 纸面上的排列方式。主题 CSS（存储在 `resume-templates/` 目录的独立 CSS 文件中）定义字体族、颜色方案、字号层级、行距和区块间距等视觉风格变量。用户自定义 CSS 以最高优先级覆盖默认主题样式。用户切换模板时只需替换主题 CSS 文件的引用，布局和内容不变，实现视觉风格的即时切换。

**5.4.4 Electron PDF 导出实现**

PDF 导出功能基于独立的 Electron 微服务实现。微服务创建 Express HTTP 服务器监听 9999 端口，接收前端发送的完整 HTML 页面（包含简历内容、布局模板和主题 CSS），在隐藏的 BrowserWindow 中加载并渲染，轮询检测页面渲染完成状态后调用 `webContents.printToPDF()` 生成 PDF Buffer，参数设置为 A4 尺寸（210mm × 297mm）、自定义边距、页眉模板（显示简历名称）和页脚模板（显示页码 / 总页数），返回 PDF 二进制数据给调用方后清理临时文件。

前端通过 `composables/useExport.ts` 封装导出逻辑，将简历的 Markdown 内容 + 主题 CSS + 自定义 CSS + 布局 HTML 模板渲染为完整的 HTML 字符串，通过 HTTP POST 发送至 Electron 微服务，收到 PDF Buffer 后通过 `URL.createObjectURL()` 创建 Blob URL 触发浏览器下载。

选择 Chromium printToPDF 而非前端 html2canvas + jsPDF 方案的核心原因是前者原生支持 CSS 分页属性，能够正确处理 A4 尺寸下的内容自动分页、页眉页脚和 @page 规则，而前端方案在分页精度（特别是跨页表格和图片）、字体渲染质量和 CSS 高级特性支持方面均有较大差距。

### 5.6 AI 参数配置模块实现

系统支持多模型、多 Key 的 AI 配置策略。管理员通过 Django Admin 后台添加 AI 模型记录，配置模型名称、调用标识（model_slug，对应 OpenAI API 的 model 参数）、API Base URL 和是否启用。用户在前端设置页面可以看到所有启用的 AI 模型，为每个模型填入独立的 API Key（存储在 `AISetting.api_keys` JSONField 中），并选择一个默认模型。

AI 调用时的 Key 解析逻辑封装在 `AIServiceHelper` 类中：首先查找用户 AI 设置中对应模型的 API Key，若未配置则回退到系统环境变量 `DEFAULT_AI_API_KEY` 中的默认 Key。当用户 AI 设置中的 `api_keys` 为空对象时，系统自动使用环境变量中的 Key，确保零配置用户也能立即使用 AI 功能（由系统承担 API 费用）。

### 5.7 关键代码实现示例

**AIServiceHelper 核心方法**

AIServiceHelper 是本系统中 AI 调用统一入口，封装了 API Key 解析、客户端实例化和请求构建的核心逻辑。其主要方法 `create_client` 接收目标模型对象（AIModel 实例）和用户对象，按优先级查找可用的 API Key：优先读取用户 AI 设置中的自定义 Key，未配置时回退到系统环境变量。返回配置好 base_url 和 api_key 的 OpenAI 客户端实例。对于支持 JSON Mode 的模型（supports_json_mode=True），在请求参数中添加 `response_format={"type": "json_object"}` 约束 AI 输出为合法 JSON；对于不支持 JSON Mode 的模型，通过在 System Prompt 末尾追加"你必须返回一个有效的 JSON 对象"指令来约束输出格式。`call_ai` 方法进一步封装了消息组装（System Prompt + User Prompt）、最大 Token 数设置和 temperature 参数的统一管理。

**PaddleOCR 单例模式实现**

```python
_ocr_instance = None

def get_ocr_instance():
    global _ocr_instance
    if _ocr_instance is None:
        from paddleocr import PaddleOCR
        _ocr_instance = PaddleOCR(
            use_angle_cls=True,
            lang='ch',
            use_gpu=False
        )
    return _ocr_instance
```

该实现确保 PaddleOCR 的模型文件在进程生命周期内只加载一次，避免每处理一个简历文件就重新初始化（每次初始化耗时 3-5 秒）。在开发环境（无 GPU）中设置 `use_gpu=False`，CPU 推理可满足单用户场景的响应需求。

**Celery 定时任务配置**

Celery Beat 配置文件定义了两类调度任务：(1) `cleanup_stale_interviews`——每 15 分钟执行一次（`schedule=900.0`），扫描并取消超时面试会话；(2) `record_daily_stats`——每日 23:50 执行（crontab 配置），记录博客文章当日统计数据（不纳入本文讨论范围）。任务通过 `@shared_task` 装饰器定义，自动注册到 Celery 任务发现机制中。

## 第七章 总结与展望

### 7.1 工作总结

本文针对当前应届毕业生在求职过程中面临的简历撰写困难和面试经验不足两大痛点，设计并实现了一款名为 AInterview 的 AI 驱动全流程求职赋能 Web 平台。系统整合 AI 模拟面试（含面部表情分析与语音识别）、智能评估报告生成、AI 对话式简历生成与管理、操作日志与 AI 参数配置等核心功能，为求职者提供从简历准备到面试实战的端到端解决方案。

本文完成的主要工作包括：

（1）**技术调研与方案选型**：对国内外在线模拟面试平台、AI 辅助简历工具和面部识别面试评估产品的现状进行系统调研，明确现有方案的局限性和本文的研究切入点。在此基础上，从技术成熟度、开发效率、成本控制和学术可复现性等维度综合评估，确定了 Python Django + Vue3 的开源全栈技术方案，选用 DeepSeek 大语言模型、PaddleOCR 引擎、face-api.js 和 Web Speech API 等核心技术组件。

（2）**系统需求分析**：从技术、经济和操作三个维度论证了项目的可行性。识别了求职者和管理员两类用户角色，明确五大核心功能模块的功能需求，并从性能、安全性、可用性和可维护性四个方面定义了非功能性需求。

（3）**系统架构设计**：设计了前后端分离的四层架构（表现层、业务逻辑层、数据层、AI 能力层），完成了六大功能模块的划分、核心业务流程设计、八张核心数据表的数据库设计和 RESTful API 接口规范定义。

（4）**系统编码实现**：完成了后端 5 个核心 Django App 的开发，包括 30+ 个 API 接口、Celery 异步任务调度、PaddleOCR 文件解析服务等。完成了前端 15+ 个页面视图的开发，包括基于 Composables 的面部表情监测和语音识别、SSE 流式追问处理、简历模板双层 CSS 渲染引擎和 Electron PDF 导出微服务集成。

（5）**AI 能力集成的工程化探索**：在 AI Prompt Engineering 方面，设计了包含角色定义、意图分类（九维度）、增量更新策略和结构化 JSON 输出的多层次 Prompt 体系，使得 AI 行为高度可控。在 Token 优化方面，增量更新策略将简历优化场景的单次输出 Token 降低至全量重写的 5%-15%；参考答案的 Redis 缓存机制避免了重复 AI 调用。

通过本项目的全流程开发，深入实践了 Django REST Framework 后端开发、Vue3 + TypeScript 前端工程化设计、MySQL 数据库建模与优化、Celery 异步任务处理、大模型 API 集成与 Prompt Engineering、实时通信技术（SSE 与 WebSocket）、OCR 引擎集成和 Electron 桌面开发等多项技术，全面锻炼了全栈开发与工程实践能力。

### 7.2 现有不足与改进方向

受开发周期和个人能力所限，本系统仍存在以下不足：

**（1）OCR 解析精度有限**

PaddleOCR 对多栏布局、图文混合排版和低分辨率图片的简历文件识别精度有待提升。实际测试中，复杂排版的 PDF 简历文本检测框排序可能出现偏差，导致提取出的文本段落顺序与原文不一致。改进方向包括：引入版面分析模型（如 PaddleStructure）对多栏布局进行结构化解析，针对简历文件这一垂直场景使用标注数据集对 PP-OCR 模型进行微调，以及增加对 Word（.docx）文件的直接解析支持（通过 python-docx 读取 XML 结构）。

**（2）AI 接口调用延迟**

面试出题和追问生成场景中，DeepSeek API 单次调用耗时通常在 3-10 秒，追问的流式推送虽然改善了用户感知，但首 Token 延迟（TTFT）仍然较高。改进方向包括：引入请求级 Prompt 缓存减少重复对话历史的 Token 传输、对于相似岗位的面试题预生成并缓存题目池、以及在生产环境部署时评估多个模型提供商根据延迟和成本动态路由。

**（3）面部识别兼容性与精度**

face-api.js 的 TinyFaceDetector 模型在光线不足或侧脸角度较大时检出率明显下降，FaceExpressionNet 的七种基础情绪分类粒度有限（无法区分"紧张"与"专注"等面试场景中更有意义的情绪维度）。此外，不同浏览器（Chrome、Edge、Firefox）对 `getUserMedia` API 的实现存在差异，在部分设备上可能出现摄像头无法启动或帧率不稳定的情况。改进方向包括：在前端增加光线不足提醒和最佳拍摄角度引导；探索使用 YOLOv11 等更先进的人脸检测模型；将情绪分为"积极/中性/消极"三级简化评估以减少分类误差的噪声影响。

**（4）语音识别依赖性**

Web Speech API 在 Chrome 浏览器中的语音识别依赖于 Google 云端语音服务，需要稳定的网络连接，在网络不稳定的环境下识别中断或延迟较大。此外，在不同操作系统和浏览器上的识别准确率和行为存在差异。改进方向包括：评估集成国产语音识别 SDK（如讯飞 Web API、百度语音）作为备用方案，以及针对面试场景的专业术语（技术名词、行业缩写等）优化识别词库。

**（5）面试评估的科学性**

当前面试评估完全依赖 AI 大模型的主观判断，缺乏与真实面试结果的对标验证数据。面部表情数据与面试表现之间的因果关系尚不明确。改进方向包括：引入面试专家的评审校准数据对 AI 评估模型进行反馈优化，以及在评估报告中标注"本评估由 AI 生成，仅供参考"的提示以管理用户预期。

**（6）系统功能完善**

当前系统尚未部署生产环境（开发环境限制），缺少自动化测试覆盖（仅完成手动功能验证），缺少用户反馈收集机制和能力持续优化的闭环。此外，系统目前仅支持单人面试模拟，不支持多人小组面试、视频回放等更丰富的面试场景。改进方向包括：编写 Django 单元测试和前端组件测试、部署到云服务器进行真实用户体验测试、增加面试录音回放和逐题复盘功能。

### 7.3 未来展望

随着大语言模型、多模态 AI 和浏览器端机器学习技术的持续进步，AI 驱动的求职赋能平台拥有广阔的发展前景。

技术层面，多模态大模型的成熟将使系统能够同时分析面试者的语言内容、语音特征（语调、语速、停顿）、面部表情和肢体语言，实现更全面的面试能力评估。浏览器端 AI（如 Chrome 内置的 Gemini Nano、WebGPU 加速推理）的能力增强将使面部识别和语音分析在客户端本地完成，进一步保护用户隐私。

应用层面，"人工智能+就业服务"模式的深入探索将为高校就业指导中心、人才市场和招聘平台提供智能化工具支持。基于大量面试数据的脱敏分析，系统可为不同专业、不同岗位的求职者提供数据驱动的备考建议和求职趋势洞察，实现从"经验驱动"到"数据驱动"的就业服务升级。
